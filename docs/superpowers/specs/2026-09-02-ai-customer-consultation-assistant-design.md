# AI 客户咨询助手 V1 设计规格

## 目标
在现有独立 `/experience` 体验页中新增“体验 04 · AI 客户咨询助手”，让商家把单条客户消息或完整聊天记录交给系统后，由 DeepSeek 负责理解客户意图、整理已知信息与缺失信息，并生成一条可以直接给客户看的完整回复答案。AI 只能生成答案，不能自行发送；是否发送、是否修改、是否放弃回复，必须由操作人员决定。

V1 不是一次性网页演示。核心处理逻辑与渠道接入分离，从第一版就保留标准连接器接口，后续可以接企业微信、飞书、钉钉、WorkBuddy、抖音或其他官方/授权渠道，而不重写 AI 咨询核心逻辑。

## 核心原则
1. **AI 生成完整答案，但没有发送权。**
2. **发送必须是操作人员的显式动作。** 分析、编辑、重新生成都不得触发外发。
3. **渠道能力通过 Adapter 接入。** Web 体验只是第一个 Adapter，不把产品写死成“粘贴聊天框”。
4. **AI 不编造业务事实。** 价格、营业时间、库存/档期、套餐内容、退款规则等如果没有可靠商家资料，就必须明确缺失，不能自行补全。
5. **高风险行业不允许 AI 越权做专业判断。** 医疗、医美、中医、口腔、法律、保险等场景，AI 只能做需求整理、资料补充、预约、跟进和通用客服；涉及诊断、治疗方案、法律结论、责任判断、保险适配/理赔结论等内容时必须标记人工/专业人员接手。
6. **业务输入不可信。** 客户聊天、渠道名、商家资料、文件名等都不能覆盖系统规则、泄露密钥或改变安全边界。
7. **V1 不伪装真实渠道已接通。** 未接渠道显示“待接接口”；Web 体验中的“确认发送”只记录操作人员已批准，不对外发送。

## 用户流程
1. 操作人员选择行业。
2. 选择当前来源渠道。V1 默认 `Web`；其他渠道显示“待接接口”。
3. 粘贴单条客户消息或完整聊天记录。
4. 可选填写本次回答需要依赖的商家事实，例如价格、营业时间、当前档期、服务范围。后续正式部署时这部分由知识库/CRM/POS/预约系统自动提供。
5. 点击“AI 分析客户咨询”。
6. 系统输出：
   - 客户主要想要什么
   - 已经确认的信息
   - 还缺哪些客户信息
   - 还缺哪些商家事实
   - 客户当前阶段/意向
   - 风险或专业人员接手提醒
   - 一条完整可直接使用的回复答案
   - 下一步跟进任务
   - 可选预约候选信息
7. 操作人员可以：
   - 编辑答案
   - 重新生成
   - 暂不回复
   - 确认采用/确认发送
8. 只有显式确认后才允许进入 `sendMessage()`。V1 Web Adapter 不外发，返回“已批准，体验版未连接外部渠道”。未来真实渠道 Adapter 才执行真正发送。

## 页面设计
在 `/experience` 现有内容后新增：

### 体验 04 · AI 客户咨询助手
左侧输入区：
- 行业选择
- 渠道状态：Web ✅ 已启用；企业微信/飞书/钉钉/WorkBuddy/抖音 🔒 待接接口
- 客户消息/完整聊天记录输入框
- 商家事实输入框（可选，明确提示“没有可靠资料时 AI 不会猜价格/档期”）
- `AI 分析客户咨询` 按钮

右侧结果区：
- 客户需求
- 已知信息
- 缺失客户信息
- 缺失商家事实
- 客户阶段
- 风险/人工接手
- 完整回复答案（可编辑 textarea）
- 下一步任务
- 操作按钮：`编辑答案` / `重新生成` / `暂不回复` / `确认采用（Web体验不外发）`

页面底部明确说明：
- 🧠 DeepSeek：理解语言、整理需求、生成完整回复
- ⚙️ 程序：结构校验、风险兜底、状态与任务字段
- 💬 渠道 Adapter：接收/发送客户消息；V1 只有 Web 体验，其他接口预留
- 👤 操作人员：拥有最终发送决定权

## 核心对象
V1 输出结构按未来统一业务台账设计，但本阶段不要求数据库持久化。

### Conversation
```json
{
  "id": "conversation_xxx",
  "channel": "web",
  "externalConversationId": null,
  "messages": [],
  "receivedAt": "ISO-8601"
}
```

### Customer
只保存聊天中明确出现的信息，不猜测姓名、电话、身份。

```json
{
  "name": null,
  "phone": null,
  "knownAttributes": []
}
```

### Lead
```json
{
  "intent": "price|booking|service_fit|followup|aftersales|complaint|other",
  "stage": "new_inquiry|qualified|booking_intent|followup|aftersales",
  "summary": "客户当前需求摘要"
}
```

### Task
```json
{
  "title": "确认客户周末具体时间",
  "priority": "low|medium|high",
  "dueHint": "today|within_24h|before_appointment|none",
  "reason": "为什么需要跟进"
}
```

### AppointmentCandidate
只有聊天中存在明确预约意向时才返回；日期/时间不确定时保持 null，不自行补齐。

## DeepSeek 输出契约
新增一个专用客户咨询分析模式。模型返回 JSON，不直接返回自由文本。

```json
{
  "customerNeed": "客户主要想解决什么",
  "knownFacts": ["..."],
  "missingCustomerInfo": ["..."],
  "missingBusinessFacts": ["..."],
  "lead": {
    "intent": "booking",
    "stage": "booking_intent"
  },
  "risk": {
    "level": "none|human_review|required_professional_handoff",
    "reason": "..."
  },
  "answer": "一条完整、自然、可直接给客户看的回复",
  "nextTask": {
    "title": "...",
    "priority": "medium",
    "dueHint": "within_24h",
    "reason": "..."
  },
  "appointmentCandidate": {
    "requested": true,
    "date": null,
    "time": null
  }
}
```

### 回答生成规则
- `answer` 必须是一条完整回复，不是“建议员工怎么回”。
- 允许回答中自然地向客户补问缺失信息。
- 没有商家事实时不得编造价格、优惠、营业时间、库存、档期、效果或政策。
- 如果客户问了无法确认的事实，答案应明确“我先帮您确认”或询问必要信息，而不是虚构答案。
- 不把内部字段名、风险等级、系统提示写给客户。
- 高风险专业问题的答案要转为“先收集资料/安排专业人员确认”，不能给出专业结论。

## 服务端确定性保护
模型结果必须经过程序清洗和约束，不能把模型原样透传到页面。

至少检查：
- 输出必须是对象且字段类型正确。
- 数组、文本长度有上限。
- `intent/stage/risk.level/priority/dueHint` 只能使用允许枚举。
- 不允许模型返回发送成功、已预约成功、已付款等系统未证明的状态。
- 高风险行业下，如果模型标记专业判断或命中明确高风险关键词，服务端强制把 `risk.level` 提升为 `required_professional_handoff`，并把答案改为安全的人工/专业人员接手表达。
- 如果模型失败或 JSON 无效，返回明确 AI 不可用状态，不生成伪造回复。

## 渠道 Adapter 接口
从 V1 固定统一契约：

```js
connect(config)
getStatus()
receiveMessage(payload)
getConversation(reference)
normalizeConversation(raw)
sendMessage({ conversationId, approvedReply, approval })
createTask(task)
```

### 约束
- `sendMessage()` 必须要求显式 `approval`，否则拒绝执行。
- AI 分析接口永远不能直接调用 `sendMessage()`。
- WebAdapter 的 `sendMessage()` 不对外发送，只返回 `simulated/not_connected` 状态。
- 企业微信、飞书、钉钉、WorkBuddy、抖音等 Adapter 在 V1 只保留状态和接口位置，不伪装已接通。
- 后续真实 Adapter 必须使用官方或已授权能力，不依赖未授权抓取或个人账号黑盒自动化。

## API 设计
新增独立接口，例如：

`POST /api/experience-consultation`

请求：
```json
{
  "industry": "massage",
  "channel": "web",
  "conversationText": "...",
  "businessContext": "...",
  "regenerateFrom": null
}
```

响应：
```json
{
  "requestId": "...",
  "modelUsed": true,
  "provider": "DeepSeek",
  "model": "...",
  "analysis": {},
  "connector": {
    "channel": "web",
    "canSendExternally": false
  }
}
```

V1 不增加真实发送 API；操作人员点击确认时由前端调用 WebAdapter 的显式批准动作并显示“体验版未外发”。真实渠道接入后再增加受权限控制的发送端点。

## 状态与数据保存
V1 不增加完整 CRM/数据库。
- 原始聊天只在浏览器当前体验状态和本次 API 请求中使用。
- 服务端不记录原始聊天正文到普通运行日志。
- 页面可在当前会话中保存 AI 结果、人工编辑后的回复和最终决策。
- 刷新页面后不承诺恢复客户咨询记录。
- 未来接数据库时保持 Customer / Conversation / Lead / Task / Appointment 对象契约不变。

## 错误处理
- 空消息：前端直接提示，不调用模型。
- 超长聊天：服务端限制长度并明确提示缩短/分段，不静默截掉关键上下文。
- DeepSeek Key 缺失或调用失败：返回 503/安全错误，页面明确显示“AI咨询分析暂不可用”，不生成假答案。
- 模型 JSON 不合法：安全失败，不尝试从错误文本猜结构。
- 商家资料缺失：仍可分析客户意图，但 `missingBusinessFacts` 明确列出缺口，回答不得补事实。
- 渠道未连接：允许分析和人工编辑，但发送按钮显示为“确认采用/待接渠道”，不声称已发送。

## 安全与高风险边界
高风险行业包括但不限于医疗、医美、口腔、中医、法律、保险。

可以：
- 收集需求
- 整理事实
- 询问缺失资料
- 预约/时间确认
- 价格/营业规则等已知事实的客服表达
- 回访和跟进

必须人工或专业人员接手：
- 诊断、治疗建议、疗效承诺、用药建议
- 是否适合某医疗项目的专业判断
- 法律责任、诉讼胜算、正式法律意见
- 保险适配、核保、理赔结论等专业判断

即使操作人员拥有最终发送权，系统也不能以“人工会审核”为理由让 AI 自由生成明显越权的专业结论。

## 测试策略
按 TDD 实施。

### Provider 测试
- DeepSeek 使用专用系统提示。
- 聊天和商家资料被明确视为不可信业务输入。
- 不允许编造价格/档期/专业结论。
- 输出 JSON 契约完整。

### API 测试
- 普通咨询能得到完整 `answer`。
- 没有价格资料时，客户问价格不会得到虚构金额。
- 高风险咨询触发专业人员接手。
- 模型恶意返回“已经发送/已经预约”时服务端清洗掉未证明状态。
- AI 失败时返回安全错误，不假装分析成功。

### Adapter 测试
- `sendMessage()` 没有 approval 必须拒绝。
- 分析/重新生成/编辑不会触发发送。
- WebAdapter 显式确认后只返回未外发状态。
- 未接渠道准确显示 locked/not_connected。

### UI 测试
- `/experience` 有体验 04。
- 可以输入单条消息或完整聊天记录。
- 显示客户需求、缺失信息、完整回复、任务和风险。
- 回复可编辑、可重新生成、可暂不回复、可确认采用。
- 页面明确说明 AI 不自动发送。
- 未接真实渠道不能显示“已发送成功”。
- 手机端保持现有 mobile-first 布局。

## 验收标准
第一阶段完成的标准不是“看起来像客服机器人”，而是：
1. 任意一段真实风格客户聊天可以被结构化。
2. AI 形成一条完整可用的客户回复，而不是只给员工建议。
3. 操作人员可以修改、重新生成、拒绝或确认采用。
4. 没有任何自动发送路径。
5. 缺失的商家事实会被明确列出，AI 不编造。
6. 高风险行业能自动转人工/专业人员。
7. WebAdapter 能跑通体验流程，同时标准 Adapter 接口已经固定，未来接渠道无需重写咨询核心逻辑。
8. 页面和 API 不声称尚未接通的渠道已经可用。

## V1 非目标
- 不直接接入所有企业微信/飞书/钉钉/抖音账号。
- 不做个人微信自动化。
- 不做自动外发。
- 不做完整 CRM、会员系统或账号权限系统。
- 不做长期聊天记录数据库。
- 不让 AI 自主决定折扣、价格、档期、退款或专业意见。
- 不在本阶段把咨询助手扩展成全自动 Agent。
