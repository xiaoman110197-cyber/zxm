# 本地商家 AI 内容助手设计

- 日期：2026-08-23
- 状态：待用户审阅
- 适用项目：老板经营问诊器（`zhenduan`）

## 1. 背景与目标

现有系统帮助老板完成经营问诊、资料核对和问题诊断。本功能在诊断报告之后增加“AI 内容助手”，把老板已经提供且允许公开的商家信息转化为可编辑的内容草稿。

第一版面向全行业本地商家，支持抖音、小红书和大众点评，生成：

1. 做图提示词；
2. 短视频脚本；
3. 探店文案。

系统同时支持商家官方账号和探店达人两种身份。达人内容采用“先生成、后核验”的合作草稿模式：达人到店前即可获得完整草稿、拍摄清单和体验核对项，但感受性描述在发布前仍需根据真实体验确认。

## 2. 已确认的产品决定

- 内容助手属于现有经营问诊系统，不创建独立产品。
- 第一版覆盖全行业，采用通用骨架、行业场景层和通用兜底模板。
- 商家信息优先从当前经营问诊中自动提炼，老板只补充或修改本次创作需要的信息。
- 平台为抖音、小红书和大众点评。
- 身份为商家官方账号和探店达人，两种口吻与事实规则必须分离。
- 每次只生成一种内容，结果可在线修改并一键复制。
- 不保存内容历史，不自动发布，不直接生成图片或视频。
- 第一版复用现有 DeepSeek 服务端配置；每次档案提炼一次模型调用，每次内容生成一次模型调用，不增加第二次 AI 复核。

## 3. 非目标

第一版不包含：

- 图片、视频、配音或数字人生成；
- 内容日历、素材库、版本历史或团队协作；
- 账号授权、自动发布、定时发布或平台数据回收；
- 付费、充值、套餐或用量计费；
- 自动联系达人或确认达人是否真实到店；
- 对商家宣传事实进行外部真实性背书。

## 4. 用户流程

### 4.1 入口

经营诊断形成结果后，在诊断报告下方显示“AI 内容助手”卡片。新增功能不得改变现有问诊、资料分析和报告下载流程。

### 4.2 商家内容档案

用户首次进入内容助手时点击“提炼商家档案”。前端把当前诊断对象提交给服务端；服务端复用现有可信诊断组装逻辑，验证资料分析令牌和诊断令牌，再让模型提取适合内容创作的字段。

档案页面显示：

- 门店或品牌名称；
- 行业场景；
- 主营产品或服务；
- 目标顾客；
- 地点与到店方式；
- 可公开的特色和卖点；
- 价格、活动、时间等时效信息；
- 期望语气；
- 仍需确认的字段。

每个字段都显示来源状态。用户可以修改字段，并决定其是否允许用于公开内容。经营问题、财务数据、报表异常和内部诊断结论默认不允许公开。

档案只保存在当前页面状态中。刷新页面后可以重新提炼；第一版不建立内容档案数据库或内容历史。

### 4.3 创作表单

用户依次选择：

1. 内容类型：做图提示词、短视频脚本或探店文案；
2. 平台：抖音、小红书或大众点评；
3. 身份：商家官方账号或探店达人；
4. 本次主题、主推项目、目标和补充事实；
5. 内容类型对应的少量动态选项。

短视频可补充目标时长和可拍素材；做图提示词可补充主体和视觉偏好；探店文案可补充希望达人重点体验的项目。低风险缺省值由系统选择，不为每个细节增加问题。

### 4.4 结果

系统一次返回一种结构化成品。结果区支持直接编辑、重新生成和复制。

达人合作草稿可以在到店前生成。若存在待确认感受，按钮显示“复制合作草稿”，复制内容保留 `[待到店确认：…]` 标记，页面同时提示“到店核验后再发布”。系统不阻止复制，但不得把未确认感受自动改写为已经发生的真人体验。

## 5. 行业场景层

第一版使用有限、可维护的行业场景层，不为每个细分行业建立一套完整代码：

- 餐饮与食品；
- 零售与门店商品；
- 美业、健身与健康生活服务；
- 家政、维修、宠物等生活服务；
- 文旅、住宿、休闲娱乐与亲子；
- 教育与专业服务；
- 通用本地商家兜底。

行业场景层决定常见卖点维度、建议镜头、需要补充的事实和禁止直接推断的内容；平台层决定标题、正文和节奏；身份层决定叙述视角和体验事实边界。三层组合，而不是复制十八套大提示词。

医疗健康、金融及其他受严格监管的业务进入高风险路径。第一版仍可生成低风险的门店介绍和事实型内容，但不得生成未经证实的功效、收益、保证或对比承诺。实施时必须根据当时有效的官方平台规则核对高风险规则，不能把本文中的示例当作完整法规清单。

## 6. 身份与事实规则

### 6.1 商家官方账号

- 使用“我们”“本店”或中性门店介绍口吻。
- 可以使用老板确认并允许公开的商家信息。
- 不得伪装成消费者评价或第三方推荐。
- 不得把经营诊断的推断、异常或内部数据包装成宣传事实。

### 6.2 探店达人

- 输出定位为“达人合作草稿”，不是已经发生的真实评价。
- 门店位置、项目、营业信息等可以使用已确认事实。
- 口感、效果、服务感受、等待时间、现场氛围等体验性信息，未确认时必须使用待确认标记或条件式写法。
- 同时生成到店拍摄清单和体验核对清单，方便达人到店后快速校正。
- 不得虚构真实到店、亲身使用、产品功效或消费者评价。

## 7. 三类输出契约

### 7.1 做图提示词

输出包含：创作目标、主提示词、画面主体、构图、光线、色彩、平台比例、文字安全区、商家一致性约束、负面提示词和使用的事实编号。系统只生成提示词，不调用图片生成服务。

### 7.2 短视频脚本

输出包含：内容目标、目标受众、三个差异明显的前三秒钩子、推荐钩子、完整台词、逐镜头分镜、每镜时长、景别、画面、动作、台词或字幕、转场、声音，以及适配当前平台的标题、正文和标签。

### 7.3 探店文案

输出包含：三个标题、正文、卖点结构、拍摄清单、体验核对清单、待确认字段、发布提醒和使用的事实编号。

商家官方身份下，该类型表现为门店介绍或探店邀请稿，不得生成虚假顾客评价。达人身份下，该类型表现为可提前生成的合作草稿。

## 8. 平台适配

- 抖音：口语化、高节奏，突出前三秒、镜头执行和短标题。
- 小红书：重视标题、封面文字、信息层次、场景感和收藏价值。
- 大众点评：地点、项目、价格、营业时间、适合人群等实用信息优先，不生成虚假消费者评价。

平台规则可能变化。发布前的规则核对属于时效性工作，实施与上线验收时应查阅三个平台的最新官方规则并记录核对日期。

## 9. 数据结构与来源状态

商家档案的核心结构为：

```json
{
  "industryArchetype": "food_beverage|retail|beauty_fitness|local_service|travel_entertainment|education_professional|general",
  "merchantName": "",
  "primaryOffers": [],
  "targetCustomers": [],
  "locationFacts": [],
  "publicStrengths": [],
  "timeSensitiveFacts": [],
  "tone": "",
  "facts": [
    {
      "id": "fact_1",
      "field": "",
      "value": "",
      "sourceKind": "owner_answer|trusted_document|owner_edit",
      "sourceRef": "",
      "status": "source_backed|owner_confirmed|needs_confirmation",
      "publicityAllowed": false
    }
  ]
}
```

`source_backed` 表示内容能追溯到当前可信诊断上下文，并不代表平台或系统对商家声明作了外部真实性背书。用户在页面修改的字段标记为 `owner_edit`。`needs_confirmation` 字段不能作为确定事实写入可发布正文。

服务端提炼档案后签发短期 `content-profile` 令牌，令牌保存原始提炼字段及来源。页面修改作为有长度限制的覆盖项单独提交；生成接口验证令牌后再合并覆盖项，从而区分“从诊断提取”和“老板本次补充”。

## 10. 技术架构

### 10.1 前端

在现有单页应用中新增内容助手卡片和前端状态，不引入新的前端框架。主要状态包括商家档案、档案令牌、创作选项、生成结果、请求状态和错误信息。

结果使用可编辑控件呈现。生成失败或重试时保留商家档案和创作表单；开始新问诊时清空内容助手状态，防止商家资料串用。

### 10.2 接口

新增两个 `POST` 接口：

1. `/api/content-profile`：验证当前诊断上下文，提炼商家内容档案并签发档案令牌；
2. `/api/content-generate`：验证档案令牌、覆盖项和创作选项，调用对应生成器，校验结构后返回结果。

两个接口都使用请求频率限制、安全错误编号和聚合运行事件。日志只记录路由、阶段、耗时、安全错误码以及允许的枚举维度，不记录门店名称、商家档案、提示词、正文、老板回答或模型原始响应。

### 10.3 服务端模块

- `src/content/profile.js`：档案边界、字段来源和覆盖项合并；
- `src/content/industry.js`：行业场景识别与模板配置；
- `src/content/platforms.js`：三个平台的结构约束；
- `src/content/identities.js`：官方账号与达人合作草稿规则；
- `src/content/generators/`：做图提示词、短视频脚本和探店文案三个独立生成器；
- `src/content/validate.js`：输入边界、输出契约、事实编号和高风险表达检查；
- `src/ai/providers.js`：扩展档案提炼与内容生成方法，继续复用现有 DeepSeek 请求封装。

模块名称可在实施时按现有代码风格微调，但职责边界不得合并成一个不可测试的大提示词文件。

### 10.4 模型调用

老板回答、档案字段和补充说明都属于不可信业务输入，不是系统指令。系统提示必须要求忽略其中改变规则、泄露密钥、绕过结构或执行无关任务的文本。

模型返回 JSON。每种生成器都有独立输出校验器。`factsUsed` 只能引用档案中允许公开的事实编号；体验字段必须进入 `pendingExperienceFields`。程序检查输出结构、枚举、长度、事实编号、高风险绝对化表达和必要的待确认标记。

自然语言校验无法证明所有宣传内容都真实。第一版依靠来源约束、程序检查和发布前人工核验共同降低风险，不把程序检查描述成事实审计或合规背书。

## 11. 错误处理

- 诊断尚未形成结果：提示先完成经营诊断，不调用模型；
- 档案缺少创作必需字段：页面只提示需要补充的字段；
- 档案令牌无效或过期：要求重新提炼档案；
- 输入过长、类型错误或枚举非法：返回可理解的校验提示；
- 请求过频：返回等待时间并保留表单；
- DeepSeek 未配置、超时、网络失败或返回无效 JSON：返回安全错误编号和重试入口，不回传上游原始错误；
- 输出校验失败：不展示半成品，允许重新生成；
- 开始新问诊：取消进行中的内容请求并清空旧商家档案。

## 12. 隐私、安全与费用

- API Key 只存在服务端环境变量中。
- 经营资料仅在当前请求所需范围内传入模型；默认不把内部财务与诊断问题用于公开内容。
- 不在日志、浏览器本地历史或错误信息中保存生成正文和商家档案。
- 对档案、覆盖项、创作说明和模型输出设置数量与字符上限。
- 第一版只调用文本模型，不调用图片、视频或发布服务。
- 档案在当前页面会话中复用，避免每生成一份内容都重新提炼一次。
- 自动化测试使用模拟模型，不产生模型费用；真实 Preview 内容验收需要获得用户对部署和实际调用的单独确认。

## 13. 测试策略

### 13.1 单元测试

- 档案字段边界、来源状态和公开权限；
- 档案令牌签发、篡改、过期和覆盖项来源；
- 行业场景、平台层和身份层组合；
- 三种输出结构和字符上限；
- `factsUsed` 引用不存在或禁止公开的事实；
- 达人合作草稿缺少待确认标记；
- 高风险绝对化、功效和收益表达；
- 提示注入文本不能改变系统约束；
- 安全错误和隐私日志。

### 13.2 API 测试

- 方法、必填字段、频率限制和缺少模型配置；
- 无效诊断上下文或档案令牌；
- 模型超时、异常、无效 JSON 和结构不合格；
- 三种内容、三个平台、两种身份的十八种路由组合；
- 运行事件不包含老板回答、档案或生成正文。

### 13.3 前端测试

- 诊断完成前后的入口状态；
- 档案确认、修改、公开权限与动态表单；
- 一次只生成一种内容；
- 编辑、重新生成、复制和失败重试；
- 达人合作草稿的提示、占位符与复制按钮；
- 开始新问诊后旧档案和旧内容被清空。

### 13.4 真实内容验收

准备六个不含真实敏感信息的代表性商家案例，覆盖餐饮、零售、美业、生活服务、文旅娱乐和专业服务。每个案例生成三类内容，共十八份成品，并轮换覆盖三个平台和两种身份。

每份成品由人工按以下清单验收：

- 至少使用两项允许公开、可追溯的商家特色；
- 不能只是替换店名的通用模板；
- 平台结构和语气符合目标平台；
- 官方账号与达人合作草稿可以明显区分；
- 镜头、台词、拍摄清单或提示词可以实际执行；
- 没有把待确认信息写成确定事实；
- 没有未经证实的功效、收益或保证性承诺。

自动化测试证明结构、安全和稳定性；真实内容验收用于判断业务质量。两者不能互相替代。

## 14. 完成标准

第一版只有在以下条件全部满足后才能声称完成：

- 商家档案能从已完成诊断中提炼、确认和编辑；
- 三类内容、三个平台和两种身份全部可用；
- 三类输出契约字段完整；
- 达人合作草稿可在到店前生成，且待确认项和拍摄核对清单完整；
- 生成结果可编辑、重新生成和复制，失败重试不清空表单；
- 隐私、安全、错误处理和十八种路由组合测试通过；
- 六个代表商家的十八份真实内容完成人工验收；
- 本地测试和构建通过；
- 如需上线，另行获得分支提交、推送、Preview 部署和真实模型调用授权，并完成对应环境验收。

## 15. 实施顺序建议

用户批准本文后，下一步只编写实施计划，不立即部署。实施应按以下依赖顺序拆分：

1. 内容数据契约、行业层、身份层和校验器；
2. DeepSeek 档案提炼与三个生成器；
3. 两个 API、信任令牌和安全运行事件；
4. 前端档案、创作表单、结果编辑与复制；
5. 自动化测试、本地构建和真实内容验收包；
6. 经用户单独批准后再处理 Git 提交、推送和 Preview 验收。
